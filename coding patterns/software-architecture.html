Software Architecture Patterns & Styles

Architecture patterns are reusable approaches to recurring system-level problems. Architecture styles describe the broad structural organization of a system. The line between the two can be blurry; what matters here is understanding the flow, responsibility boundaries, and trade-offs.

Based on the examples named in Wikipedia's Software architecture — Patterns and styles section. The animations below are simplified teaching models, not complete implementations.

Pattern

A reusable solution to a recurring architecture problem. Think: “When this problem appears, this arrangement is a proven way to deal with it.”

Style

A high-level structural vocabulary and set of constraints. Think: “This is how the system is organized and how its pieces are allowed to interact.”

Pattern

Model–View–Controller (MVC)

Separates application state and rules (Model), presentation (View), and input/orchestration (Controller) so changes in one concern do not have to rewrite the others.

How it works

  • The user acts through the interface.
  • The Controller interprets the action and asks the Model to change or retrieve data.
  • The Model represents application state and rules.
  • The View renders that state back to the user.

Useful when

User-interface logic, domain logic, and rendering are becoming tangled together.

Trade-off: clearer separation costs extra structure, and real frameworks vary in exactly how Controller, Model, and View communicate.

Pattern

Circuit Breaker

Stops repeatedly calling a failing remote dependency. After enough failures it “opens,” rejects calls quickly, waits, then allows a test request through before deciding whether to close again.

How it works

  • Closed: requests pass normally and failures are counted.
  • Open: requests fail fast instead of hammering the unhealthy service.
  • Half-open: a limited probe is allowed through after a cooldown.
  • If the probe succeeds, normal traffic resumes; if it fails, the breaker opens again.

Trade-off: it improves resilience but adds state, timing, thresholds, fallback behaviour, and monitoring that must be tuned.

Style

Layered Architecture

Organizes software into horizontal layers, each with a distinct responsibility. Calls usually move through neighbouring layers rather than allowing every part of the system to reach every other part directly.

Typical flow

  • Presentation handles the user-facing interaction.
  • Application/business logic applies use-case and domain rules.
  • Data-access code isolates persistence details.
  • The database stores durable state.

Useful when

You want predictable responsibility boundaries in a conventional application and the domain maps naturally to tiers.

Trade-off: layers can become pass-through bureaucracy, and a change may have to cross several layers even when little value is added.

Style

Microservices

Builds a system as independently deployable services aligned around bounded capabilities. Each service owns a focused responsibility and communicates with other services over explicit interfaces.

How it works

  • A client often enters through an API gateway or edge service.
  • Requests are routed to the service responsible for that capability.
  • Services can be deployed and scaled independently.
  • Cross-service work requires network communication and distributed coordination.

Useful when

Different parts of a large system need independent deployment, scaling, ownership, or technology evolution.

Trade-off: local code becomes simpler at the cost of distributed-system problems: latency, partial failure, tracing, deployment coordination, and data consistency.

Style

Event-Driven Architecture

Components publish events describing something that happened. Other components subscribe and react without the publisher needing to know every consumer.

How it works

  • A producer emits an event such as OrderPlaced.
  • An event broker or bus distributes it.
  • Multiple consumers can react independently: inventory, email, analytics, billing, and more.
  • New consumers can often be added without changing the producer.

Useful when

Work is naturally asynchronous, several components react to the same occurrence, or loose coupling is more valuable than immediate synchronous answers.

Trade-off: flow is less obvious than a direct call chain. Ordering, duplicate delivery, retries, observability, and eventual consistency become design concerns.
