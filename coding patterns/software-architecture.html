Software Architecture Patterns & Styles

This page is about architectural decisions, not memorizing definitions. Each pattern below is applied to the same small order-processing system so you can see what changes in the code, data, deployment boundaries, message flow, scaling model, and failure behavior.

Important: these are not five mutually exclusive choices. A real cloud application might use MVC inside a web service, layers inside each service, microservices between domains, events between services, and circuit breakers around unreliable network calls.

The set of examples is based on the patterns and styles referenced by Wikipedia's Software architecture — Pattern material. The implementation examples here are original teaching examples.

The system we will keep rebuilding

A customer submits an order for two products. The application must validate it, reserve inventory, take payment, save the order, and eventually send a confirmation.

Input: POST /orders → customer C-42, SKU KB-100 × 1, SKU MS-200 × 2.

Question: Where should each responsibility live, how should the pieces communicate, and what happens when one of them fails?

Pattern

Model–View–Controller (MVC)

MVC separates how a user request enters the application, how business state behaves, and how a response is presented. It is mainly a code-organization pattern for interactive applications—not a cloud scaling strategy.

What problem is it solving?

Without separation, request parsing, business rules, database calls, and HTML/JSON formatting can collapse into one giant handler. MVC gives each concern a home.

In our order system

  • Controller: accepts POST /orders, validates request shape, calls the model/application logic.
  • Model: represents order rules and state.
  • View: renders JSON, HTML, or another representation from the result.
Choose it when: you have a user-facing application and want a clear boundary between input handling, state/business behavior, and presentation.
Do not expect it to solve: distributed deployment, service ownership, cross-service reliability, or independent scaling.

Common languages/frameworks

ASP.NET MVC, Spring MVC, Ruby on Rails, Laravel, Django-style MVC/MTV patterns, and many JavaScript frameworks use closely related separations.

Style

Layered Architecture

Layering controls dependency direction. Higher-level code asks lower layers for capabilities instead of every part of the application reaching directly into the database or infrastructure.

Typical layers

  • Presentation: HTTP/UI concerns.
  • Application/service: orchestrates a use case.
  • Domain: business rules and entities.
  • Infrastructure/data: SQL, file systems, external APIs.

Why this matters

A request can change from REST to a message consumer without rewriting pricing rules. A database can change without teaching controllers SQL. The architecture is enforcing where dependencies are allowed.

Good fit: internal business systems, APIs, line-of-business apps, and teams that value understandable dependency boundaries over deployment independence.
Failure mode: a “layered” app where every layer is just a pass-through creates ceremony without separation. Another common failure is bypassing layers whenever something feels inconvenient.

class PlaceOrder {
  constructor(private orders: OrderRepository,
              private inventory: InventoryGateway) {}

  async execute(cmd: PlaceOrderCommand) {
    const order = Order.create(cmd.customerId, cmd.items);
    await this.inventory.reserve(order.items);
    await this.orders.save(order);
    return order;
  }
}

Style

Microservices

Microservices split a system into independently deployable services aligned to business capabilities. The important word is not “small”; it is independent: code ownership, deployment, runtime scaling, and usually data ownership are separated.

Our order system becomes

  • Order Service owns order lifecycle.
  • Inventory Service owns stock and reservations.
  • Payment Service owns charges/refunds.
  • Notification Service owns email/SMS delivery.

The architectural cost

Function calls become network calls. One transaction can no longer safely update four databases. You now need timeouts, retries, idempotency, observability, versioned contracts, deployment automation, and a strategy for partial failure.

Choose it when: parts of the system genuinely need independent release cycles, scaling, ownership, technology choices, or fault isolation.
Avoid premature microservices: a small team can easily create a distributed monolith—many deployables that still must change together.

Cloud fit

Strong. Containers, managed databases, service discovery, autoscaling, load balancers, and managed observability all support this style well. But cloud hosting alone is not a reason to use microservices.

Style

Event-Driven Architecture

A producer publishes that something happened; consumers react independently. The producer does not need to know every downstream action. This is excellent for asynchronous workflows—but introduces eventual consistency and delivery semantics you must design for.

Order example

The Order Service publishes OrderPlaced. Inventory, analytics, notifications, and fraud detection can all react without the Order Service calling them directly.

What you gain

  • Loose coupling between producer and consumers.
  • New consumers can be added without changing the producer.
  • Consumers can process at different rates and recover independently.

What becomes harder

  • Events can arrive more than once.
  • Consumers can process late or out of order.
  • There is no single synchronous transaction covering everything.
  • Debugging needs correlation IDs and event tracing.
Critical rule: design consumers to be idempotent. “At least once” delivery can otherwise charge a card or send a shipment twice.

Resilience pattern

Circuit Breaker

A circuit breaker wraps calls to an unreliable remote dependency. After repeated failures it stops making calls temporarily, fails fast, and later allows a probe to determine whether the dependency recovered.

Why it exists

Suppose Payment normally answers in 80 ms but is now timing out after 10 seconds. Without a breaker, every order request can pile up waiting for the same broken dependency, exhausting threads, connections, memory, and request queues.

States

  • Closed: calls pass normally; failures are counted.
  • Open: calls are rejected immediately for a cooldown period.
  • Half-open: a limited probe is allowed. Success closes the circuit; failure opens it again.
Use with: timeouts, bounded retries, fallbacks where appropriate, and observability. A circuit breaker is not a substitute for a timeout.
Do not: blindly retry non-idempotent operations such as charging a card. You need request IDs/idempotency keys and provider-specific guarantees.

Code

Simplified circuit breaker
async function chargeWithBreaker(request) {
  if (breaker.isOpen()) {
    throw new Error('Payment temporarily unavailable');
  }

  try {
    const result = await withTimeout(
      payments.charge(request), 1200
    );
    breaker.recordSuccess();
    return result;
  } catch (err) {
    breaker.recordFailure();
    throw err;
  }
}

Putting it together

What a realistic cloud system might actually use

The useful mental model is composition. Architecture patterns operate at different levels.

Inside one service

HTTP Controller ← MVC / presentation boundary ↓ Application Service ← Layered orchestration ↓ Domain Model ← business rules ↓ Repository Interface ← dependency boundary ↓ PostgreSQL Adapter

Between services

Order Service ├──sync HTTP──→ Payment Service │ ↑ Circuit Breaker + timeout │ └──event──────→ Message Broker ├──→ Inventory Consumer ├──→ Notification Consumer └──→ Analytics Consumer Each service may itself use MVC + layers internally.

A practical decision sequence

  1. Start by separating responsibilities inside one deployable application.
  2. Use layers or similar dependency boundaries where they make the code easier to reason about.
  3. Use MVC when you have interactive/request-driven presentation concerns.
  4. Split into microservices only when independent deployment/ownership/scaling is worth the distributed-systems cost.
  5. Use events where asynchronous decoupling is valuable.
  6. Add circuit breakers around remote calls where repeated failure can cascade.
